# 报告撰写模块

## 1. 模块组成

报告撰写模块由“报告服务”和“报告撰写 Skill”两部分组成。

- 报告服务负责真正执行工作，包括读取记录、校验状态、数据清洗、调用知识库和互联网检索、组织证据、调用大模型、检查输出、套用 Word 模板、生成文件、保存版本和返回结果。
- 报告撰写 Skill 负责告诉 Agent 在什么情况下生成报告、必须收集哪些信息、怎样调用报告服务、怎样解释结果、哪些内容必须复核。Skill 本身不应承担数据库连接、联网检索、模型密钥、Word 排版和文件存储等核心能力。
- 现有 Streamlit 系统、未来的知识图谱系统、数据库系统或其他业务系统都应调用同一个报告服务。这样报告能力只维护一套，不需要在每个系统里重新编写一套 Agent 流程。

整体关系如下：

```text
现有工作台 / 知识图谱 / 业务数据库 / 其他系统
                    │
                    ▼
              数据适配和权限校验
                    │
                    ▼
                 报告服务
      ┌─────────────┼─────────────┐
      ▼             ▼             ▼
   本地知识库     互联网检索     大模型服务
      └─────────────┼─────────────┘
                    ▼
          证据整理和报告质量检查
                    ▼
        Word 模板处理、文件和版本存储
                    ▼
           预览、下载、审核和定稿

Agent ──按照报告撰写 Skill──调用报告服务
```

## 2. 报告服务的职责

报告服务应成为独立、可复用的业务能力，主要负责以下内容：

1. 接收来源系统、任务、记录、报告配置和模板信息。
2. 根据用户和项目权限读取服务端正式数据。
3. 检查记录是否正式提交，防止草稿进入正式报告。
4. 清洗和标准化输入字段，形成可用于决策的批次事实。
5. 读取路线决策、工艺方案和数据质量结果。
6. 从本地文献、知识图谱、业务数据库和互联网收集证据。
7. 对证据去重、分级、编号，并保留来源地址和检索时间。
8. 生成大模型提示词并调用真实大模型。
9. 检查章节完整性、事实边界、引用、篇幅和禁用内容。
10. 读取并套用 Word 模板，生成可编辑文档。
11. 保存报告、来源、输入快照、模型信息、生成时间和版本。
12. 向调用系统返回预览内容、状态、来源、复核项和 Word 文件。

报告服务不能依赖某一个页面。页面只是调用入口，核心逻辑必须可以被知识图谱、数据库任务、批处理程序和其他 Agent 重复使用。

## 3. 报告撰写 Skill 的职责

报告撰写 Skill 应解决以下问题：

- 识别用户是否在要求生成、续写、修改、审核或导出项目报告。
- 判断当前任务是否有正式提交的 `task_id` 和 `record_id`。
- 缺少关键身份或报告基础信息时，向用户补充询问。
- 将用户要求转换为报告服务可以接收的标准参数。
- 调用创建报告、查询状态、读取报告、重新生成和下载 Word 等工具。
- 把服务返回的缺失信息和待复核项用简单语言告诉用户。
- 修改报告时使用原报告版本和用户的具体修改要求，不重新猜测整套数据。
- 不直接编造产量、价格、市场规模、投资额、收益率、政策、标准或论文。
- 不在 Skill 中保存模型密钥，不直接操作数据库，不自己拼接 Word 文件。

Skill 是 Agent 的操作说明和调用规范；报告服务是实际执行引擎。其他系统如果不使用 Agent，也可以直接调用报告服务。

## 4. 当前已经实现的服务基础

现有代码已经形成第一版报告服务模块：

```text
app/reporting/
├── __init__.py
├── service.py
├── web_search.py
└── docx_export.py
```

- `service.py`：组织研究问题、本地证据、互联网证据、大模型提示词、报告生成结果和文件返回。
- `web_search.py`：执行 Tavily、DuckDuckGo 和 Bing RSS 检索，记录来源和错误。
- `docx_export.py`：读取 Word 模板、替换占位符、生成封面、目录、标题、正文、表格、超链接、页眉页脚和页码。
- `app/intake_pipeline.py`：提供清洗后的批次事实、数据质量分、路线排序、工艺阶段和任务上下文。
- `app/intake_store.py`：保存采集记录、状态、固定 `task_id` 和 `revision`。
- `app/ui/industry_pages.py`：负责现有 Streamlit 页面与报告服务之间的调用。

当前属于“应用内部服务模块”，已经实现统一入口和可测试逻辑，但还不是可以被其他系统通过网络调用的独立服务。

## 5. 标准输入

报告服务的标准输入建议固定为以下结构：

| 字段 | 含义 | 要求 |
| --- | --- | --- |
| `source_system` | 数据来自工作台、知识图谱或业务数据库 | 必填 |
| `user_id` | 当前用户或调用主体 | 必填 |
| `project_id` | 所属项目 | 必填 |
| `task_id` | 同一业务任务的固定编号 | 必填 |
| `record_id` | 本次报告使用的记录编号 | 必填 |
| `revision` | 记录修改版本 | 必填 |
| `record_status` | 草稿或正式提交 | 必须为 `submitted` |
| `record` | 一条原始业务记录 | 必填 |
| `cleaned_facts` | 标准化后的事实 | 可由服务生成 |
| `decision_result` | 路线评分和推荐路线 | 可由服务生成 |
| `process_plan` | 工艺阶段和复核状态 | 可由服务生成 |
| `report_profile` | 项目名称、单位、地区、周期、目的等 | 必填 |
| `template_file` | 用户上传的 `.docx` 模板 | 选填 |
| `requested_changes` | 修改已有报告时的具体要求 | 修改时必填 |
| `previous_report_id` | 被修改的报告版本 | 修改时必填 |

一份报告当前只允许绑定一个 `record_id`。以后需要多批次汇总时，应新增明确的“汇总报告”类型，不能悄悄把多条记录混在单批次报告中。

## 6. 数据来源适配

不同系统的数据结构不同，报告服务前面需要设置适配器，将数据转换成统一事实结构。

### 6.1 现有工作台

工作台通过 `task_id + record_id` 读取正式提交的采集记录，生成清洗结果、路线决策和工艺方案，再交给报告服务。

### 6.2 知识图谱

知识图谱适配器应完成：

- 根据任务中的实体标识读取品种、产地、企业、产品、工艺、政策和文献实体；
- 保留每个事实的实体编号、关系、属性、来源和更新时间；
- 把推理结果与原始事实分开；
- 将图谱证据转换成统一的 `title、source、content、retrieved_at、source_type` 结构；
- 不把没有来源的推断当成确定事实。

### 6.3 业务数据库

数据库适配器应完成：

- 使用服务账号和最小权限读取指定记录；
- 按字段映射表转换名称、单位、日期、状态和枚举值；
- 记录数据库名称、表或视图、主键和更新时间；
- 不允许 Agent 自由编写并执行任意 SQL；
- 敏感字段在进入大模型前脱敏或排除。

### 6.4 互联网

互联网检索根据产地、品种、目标产品、区域和报告目的自动生成查询。优先使用官方统计、政府网站、国家标准平台、论文原文和权威行业资料。新闻、企业宣传和搜索摘要可以作为线索，但需要降低证据等级。

## 7. 完整生成流程

1. 来源系统创建或选择业务任务，确定 `task_id`。
2. 用户填写或系统读取一条业务记录，形成 `record_id`。
3. 草稿阶段只保存和校验，不生成路线、工艺和报告。
4. 用户正式提交记录，服务端确认权限和 `submitted` 状态。
5. 系统清洗字段，统一单位、日期、名称和数值，识别缺失项、异常项和无效项。
6. 系统计算数据质量分，判断哪些字段可以参与决策。
7. 系统生成路线排序和基础工艺方案，并列出限制条件和待验证内容。
8. 报告服务读取项目名称、使用单位、区域、周期、工作目的和 Word 模板。
9. 报告服务从本地知识库、知识图谱、数据库和互联网查询补充资料。
10. 证据层对来源进行去重、编号和分级，区分用户事实、外部事实、工程建议、模型推断和待确认内容。
11. 提示词生成器把标准事实、决策结果、工艺方案、证据和报告要求发送给大模型。
12. 大模型生成完整项目报告，重要外部结论使用来源编号。
13. 质量检查器检查18个章节、篇幅、引用、禁用表述、虚构数字、工艺参数边界和待复核项。
14. 检查不通过时进行受控修订；多次失败则返回明确错误，不生成假报告。
15. Word 引擎读取用户模板或系统模板，生成可编辑 `.docx`。
16. 服务保存报告正文、Word 文件、来源清单、输入快照、模型、提示词版本、生成时间和报告版本。
17. 调用系统显示预览，并提供 Word 下载、人工审核、修改和定稿操作。

## 8. 证据和事实边界

报告中的内容应使用以下分类：

| 类型 | 内容 | 报告写法 |
| --- | --- | --- |
| 正式提交事实 | 产地、品种、批次、数量、糖度等 | 可以直接陈述，并标明来自本次记录 |
| 本地证据 | 本地论文、标准、内部资料 | 标明来源和适用条件 |
| 图谱或数据库事实 | 有实体、主键和更新时间的数据 | 标明系统来源和更新时间 |
| 互联网证据 | 官方统计、政策、论文、行业资料 | 使用来源编号和网址 |
| 工程建议 | 路线、设备、试验和建设建议 | 明确写成建议或待验证方案 |
| 模型推断 | 根据多项信息形成的判断 | 明确写成分析判断，不能冒充原始事实 |
| 待确认内容 | 投资额、收益率、产能、价格等缺少依据的信息 | 写“待补充”“待询价”或“待测算” |

来源记录至少应包含：

```text
source_id
source_type
title
url_or_record_reference
snippet_or_fact
publisher
published_at
retrieved_at
query
evidence_level
```

## 9. 大模型生成规则

- 必须使用真实大模型调用，不能用固定段落拼成一份看起来已经完成的报告。
- 输入只包含本次任务需要的数据，不能把 Word 二进制、旧报告全文、无关会话和密钥发送给模型。
- 报告类型当前固定为项目报告。
- 章节必须完整，正文需要形成连续论证，不只是项目符号列表。
- 重要外部结论必须带来源编号。
- 没有依据的数字不得生成确定值。
- 单篇论文中的实验条件不得直接变成企业生产参数。
- 投资、收益、市场规模和产能结论必须有询价、订单、工程量或统计依据。
- 模型返回内容过短、章节缺失或证据引用异常时，应判定失败并重新生成或返回错误。
- 每次调用应记录模型名称、提示词版本、耗时、状态和错误类型，不能记录密钥。

## 10. Word 模板流程

### 没有上传模板

使用系统项目报告格式，自动生成：

- 封面；
- 静态目录或可更新目录；
- 分级标题；
- 正文和列表；
- 可编辑表格；
- 可点击来源链接；
- 页眉、页脚和页码；
- 参考资料和待人工复核项。

### 上传单位模板

1. 限制为 `.docx` 文件，并检查大小和文件结构。
2. 读取模板页面设置、样式、页眉、页脚和已有内容。
3. 替换项目名称、单位、部门、人员、区域、周期、目的和章节占位符。
4. 模板缺少部分章节时，将缺失章节追加到模板正文。
5. 生成的新文件保持可编辑，不把报告转换成图片。
6. 输出前进行结构检查和逐页渲染检查。

建议统一占位符：

```text
{{项目名称}}
{{使用单位}}
{{承办部门}}
{{经办人员}}
{{统计区域}}
{{报告周期}}
{{工作目的}}
{{项目摘要}}
{{项目背景}}
{{市场需求与竞争环境}}
{{加工路线和工艺方案}}
{{投资估算与资金使用方向}}
{{风险分析与应对措施}}
{{参考资料}}
{{待人工复核项}}
```

## 11. 服务接口

当前 Python 调用入口可以继续保留：

```python
generate_project_report(
    task_id=task_id,
    record_id=record_id,
    document=document,
    analysis=analysis,
    profile=report_profile,
    template_path=template_path,
)
```

拆成独立服务后，建议提供以下接口：

```text
POST /v1/project-reports
GET  /v1/project-reports/{report_id}
GET  /v1/project-reports/{report_id}/status
GET  /v1/project-reports/{report_id}/document
POST /v1/project-reports/{report_id}/revisions
POST /v1/project-reports/{report_id}/finalize
```

创建报告时立即返回：

```json
{
  "report_id": "report_xxx",
  "task_id": "task_xxx",
  "record_id": "ic_xxx",
  "revision": 1,
  "status": "queued"
}
```

完成后返回：

```json
{
  "report_id": "report_xxx",
  "status": "completed",
  "report_type": "项目报告",
  "markdown": "完整报告正文",
  "sources": [],
  "review_items": [],
  "document_url": "受权限控制的 Word 下载地址",
  "created_at": "时间",
  "model": "实际使用的模型",
  "prompt_version": "版本"
}
```

相同的 `task_id + record_id + revision + 报告配置版本` 应生成稳定的幂等键，避免用户重复点击后创建多份相同任务。

## 12. 任务状态

建议使用以下状态：

```text
draft
submitted
queued
cleaning
researching
writing
validating
rendering
completed
failed
needs_review
finalized
```

页面可以根据状态显示实际进度。生成失败时保存失败阶段和错误类型，重新执行时从安全的阶段开始，不能把失败结果标记为完成。

## 13. 报告撰写 Skill 文件结构

建议建立独立 Skill：

```text
report-writing-skill/
├── SKILL.md
├── references/
│   ├── report-input-schema.md
│   ├── report-output-schema.md
│   ├── evidence-policy.md
│   ├── project-report-sections.md
│   └── service-api.md
└── examples/
    ├── create-report.json
    ├── revise-report.json
    └── review-report.json
```

`SKILL.md` 应写明：

1. 什么请求需要使用该 Skill。
2. 生成前必须存在的任务、记录和正式提交状态。
3. 报告配置需要哪些字段。
4. 怎样调用创建、查询、修改、下载和定稿工具。
5. 怎样处理缺失信息和服务错误。
6. 怎样向用户展示报告状态、来源和待复核项。
7. 哪些数据不能发送给模型。
8. 哪些内容禁止模型自行编造。
9. 什么时候必须要求人工审核。
10. Skill 不直接操作数据库、搜索网站、模型密钥和 Word 文件，全部通过报告服务完成。

## 14. 其他系统接入方式

### 方式一：系统直接调用报告服务

适合数据库后台任务、批量生成、定时生成和固定业务流程。系统准备标准输入后调用服务，不需要经过 Agent。

### 方式二：Agent 使用报告撰写 Skill

适合用户用自然语言提出“根据当前批次写项目报告”“把风险章节写得更详细”“按照单位模板重新生成”等请求。Agent 通过 Skill 收集参数并调用服务。

### 方式三：系统页面和 Agent 同时使用

页面按钮负责确定性操作，Agent 负责解释、修改和补充。两者都调用同一个报告服务，并使用同一个 `task_id + record_id`，避免出现两个互不一致的报告流程。

## 15. 权限、存储和审计

- 调用方必须携带用户和项目身份，服务端重新校验记录权限。
- 模型密钥、搜索密钥和对象存储密钥只放在服务端 Secrets 中。
- Word 模板、报告和附件存放在受权限控制的对象存储中，数据库只保存元数据和文件地址。
- 报告下载地址应短期有效，不能公开暴露所有报告。
- 输入快照、来源、模型版本、提示词版本、报告版本和人工修改记录需要可追溯。
- 删除、定稿、覆盖正式版本和改变访问权限需要单独授权。
- 个人信息、联系方式、合同、价格和内部经营数据在进入模型前按业务规则脱敏。

- 应用内部报告服务模块；
